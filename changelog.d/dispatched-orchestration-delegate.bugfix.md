## A dispatched orchestration can delegate to its own workers again — and a delegate that reaches nobody now says so

An orchestration started with `dot-agent-deck dispatch --orchestration <name>` came up looking perfect and could not do the one thing an orchestration is for. Every role pane spawned, every card was named, the tab surfaced live, and the orchestrator was handed a context file explaining exactly how to delegate — but every `dot-agent-deck delegate --to <role>` it then ran was silently dropped. No worker ever received a task, and the daemon log recorded only `delegate from unknown pane`. Starting the same orchestration the normal way, with `Ctrl+N`, worked.

The cause was that the daemon learned about orchestration roles in exactly one place: the handler behind the TUI's "start this agent" request. That is the path a `Ctrl+N` orchestration takes, and the only path that went through it. An orchestration the daemon spawns *itself* — `dispatch --orchestration`, a scheduled fire, or issue dispatch — goes straight to the spawn primitive, so its panes were never recorded as belonging to an orchestration and its orchestrator was never recorded as being one. The delegate arrived, found no role for the sender, and returned. Both spawn paths now register through a single shared function, so the two cannot drift apart again.

The second half of the report was that none of this was visible. `delegate` was fire-and-forget: it sent the signal and exited 0 without waiting to hear whether anything had happened. So an orchestrator whose delegation had been dropped was told it succeeded, announced that its worker was now working, and waited forever for a completion signal that could never arrive — which is how a routing bug turned into a hung orchestration rather than an error message.

`delegate` now waits for the daemon's answer and reports it. A delegate that cannot be routed — from a pane that carries no orchestration role, or from a pane that is not its orchestration's orchestrator — exits non-zero and prints what could not be resolved, naming the pane. So does a delegate that names a role this orchestration has no pane for, which previously also exited 0 having reached nobody. An orchestrator can now tell a delegation that landed from one that did not, which is the difference between reporting progress and inventing it.

Mixed versions keep working in both directions. An older `delegate` against a newer daemon is unaffected, and a newer `delegate` against an older daemon — which does not answer on this verb — treats the silence as the previous contract and still exits 0, rather than reporting every delegation as broken.
