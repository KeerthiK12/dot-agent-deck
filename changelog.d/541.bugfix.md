## Concurrent dispatches no longer fail on each other's half-created worktree

Dispatching several agents at once could fail one of them before any agent ran, with `fatal: failed to read '.git/worktrees/<name>/commondir': Success`. The `Success` is the tell: git prints `strerror(errno)` for an errno nothing ever set, so the read came back short rather than failing. `git worktree add` scans the repository's worktree list before creating its own entry and reads every entry's `commondir`; another `git worktree add` that has created its entry but not yet written that file — two adjacent syscalls apart — makes that read come back empty. The loser died in the setup step, so the visible symptom was a dispatch failing for reasons unrelated to anything it was asked to do. A busy filesystem made it markedly more likely by widening the window.

Worktree creation is now serialized per repository across processes, keyed on `git rev-parse --git-common-dir` so every spelling of one repository (the main checkout, any of its linked worktrees, a relative path) lands on one lock — separate decks serialize against each other, not merely tasks inside one. Serialization cannot cover an add the deck did not start, so `git worktree add` is additionally retried a bounded number of times (four backoffs, 1.5s in total) on that one signature. Nothing is swallowed: a `commondir` that stays unreadable — what a crashed add leaves behind — still surfaces as an error, and every other `git worktree add` failure stays a hard failure with git's own message. If the lock cannot be taken at all, creation proceeds unserialized rather than wedging the dispatch.

Serializing creation also made one pre-existing misclassification reachable by design rather than by luck, so it is fixed here too: a second dispatch of a name whose worktree is still **there** is now reported as a live claim ("already claimed by another dispatch") instead of as a leftover branch whose "worktree is already gone" — which sent the user to `git branch -D` for a tree another dispatch was working in. A name whose worktree really is gone still reports the leftover branch, unchanged.

The retry also repairs a second-order failure that made the first one sticky. An add that dies on the scan has already created its `-b` branch, so a naive retry failed with `a branch named … already exists` — and because a dispatch refuses to reuse an existing branch (it may hold committed work), the dispatch name stayed poisoned until the branch was deleted by hand. The branch is now re-probed on each attempt and attached rather than re-created.
