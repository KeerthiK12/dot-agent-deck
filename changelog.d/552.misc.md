## A Windows clone's broken symlinks are now caught instead of ignored

The repository tracks 35 symlinks, and two of them carry real behaviour: `AGENTS.md` → `CLAUDE.md` is how Codex and OpenCode read the same project conventions Claude does, and the 33 entries under `.agents/skills/` are how they reach the same skills tree. Git materialises a symlink as a link only when `core.symlinks` is on, which on Windows requires Developer Mode or an elevated clone; otherwise it silently writes a plain text file containing the target path. `AGENTS.md` becomes a 9-byte file reading `CLAUDE.md`, and an agent that reads it does not error — it proceeds with no project instructions at all, looking exactly like a correctly configured agent that has nothing to follow.

`scripts/check-symlinks.sh` now asserts that every tracked symlink resolves to its target, naming each offender in the terms someone who has never heard of `core.symlinks` can act on. It compares content rather than asking `test -L`, which on Windows answers a question about the shell rather than about the checkout, and it refuses to report success when it found nothing to check. CI's `build-windows` job runs it right after checkout — preceded by `--self-test`, which materialises the index with `core.symlinks=false` and requires the checker to reject that tree, so the green result is never the vacuous kind.

CI can only guard the runner, never a contributor's own working tree, so `CONTRIBUTING.md` now tells Windows contributors to enable symlinks before cloning and how to verify, and [`docs/develop/windows-symlinks.md`](https://github.com/vfarcic/dot-agent-deck/blob/main/docs/develop/windows-symlinks.md) records the mechanism, the repair for a clone that already came out wrong, and why the symlinks are worth keeping. No released binary is affected: `release.yml` builds only the Apple and Linux targets.
