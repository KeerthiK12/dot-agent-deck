## Your Claude Code settings survive `hooks uninstall`, a co-located hook, and an interrupted write

Three ways dot-agent-deck could destroy configuration in `~/.claude/settings.json` — a file it does not own — are fixed together, because they were one problem seen from three sides.

`hooks uninstall --agent claude-code` used to read the settings file leniently: anything it could not parse, down to a single trailing comma, was treated as an empty config and written back as `{}`, destroying the user's `model`, `env` and `permissions` (including `permissions.deny`) while reporting success and exiting 0. Uninstall now applies the same contract install got in the previous release — only a *missing* file means "nothing to uninstall", a file that cannot be read or parsed is left byte-for-byte as found with a backup preserved at `settings.json.bak`, and the refusal reaches the shell as a message on stderr and a non-zero exit ([#522](https://github.com/vfarcic/dot-agent-deck/issues/522)). Uninstall also no longer rewrites the file at all when none of the deck's hooks were in it, so it can neither reformat settings it did not change nor create a `settings.json` on a machine that never had one.

A single hook rule's `hooks` array is a list of commands sharing one matcher, so putting your own hook in the same rule object as the deck's is a normal thing to do — and both install and uninstall used to delete that whole rule object, taking your command with the deck's. A user's `/usr/local/bin/my-critical-audit.sh` disappeared on `hooks uninstall` with nothing said about it, and because hooks are auto-installed at every dashboard startup, simply opening the deck was enough to lose it. Removal is now per command: only the deck's own command is taken out of a shared rule, the rule keeps its matcher and every other command, and a rule is dropped only once nothing is left in it ([#535](https://github.com/vfarcic/dot-agent-deck/issues/535)).

Finally, the deck wrote `settings.json` by truncating it in place — over a file two deck processes and your editor all write. Claude Code reading inside that window saw an empty file, a crash mid-write left a permanently truncated one, and two decks starting at once could lose each other's updates. The file is now published by writing a temp file in the same directory and renaming it over the destination, serialized by an in-process lock, so a reader sees either the whole old file or the whole new one and an interrupted write leaves the original intact ([#534](https://github.com/vfarcic/dot-agent-deck/issues/534)) — closing the very hole that manufactures the unparseable settings file the refusals above exist to protect.

Two smaller behaviour changes come with that publish. An existing `settings.json` keeps its own permissions exactly (a file you had kept at 0600 is not widened to 0644), and a settings file the deck creates from scratch is now owner-only. A `settings.json` that is a *symlink* — a dotfiles arrangement — is now refused rather than silently replaced with a regular file; point it at a real file, or edit the linked file's hooks by hand.
