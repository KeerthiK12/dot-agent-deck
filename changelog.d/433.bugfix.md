## The orchestrator is no longer pointed at a work-done summary the deck failed to write

When a worker reported `work-done`, the deck wrote its report to `.dot-agent-deck/work-done-<role>.md` and then told the orchestrator to go read it. Writing the file was best-effort — it can fail because no working directory was recorded for the pane, because `.dot-agent-deck` cannot be created, or because the write itself fails — but the instruction to read it was sent regardless.

The dangerous case is not the missing file; it is the file that is already there. That path is keyed by role name alone and reused for every delegation to that role, so a failed write left the *previous* delegation's report sitting at it. The orchestrator read a report that was complete, well-formed, from the right role, and about the wrong task, with nothing in the content, the pointer, or the pane to distinguish it from the current one — and then made decisions about work that had never been done. The only trace was a warning in the daemon log, and one of the three failure paths did not even leave that.

The deck now tells the orchestrator that the file is unavailable and inlines the worker's report into the feedback instead, so a failed write degrades to a worse-formatted report rather than a confidently wrong one. It costs nothing: the deck is still holding the report in memory at the moment it gives up on the file. An inlined report is collapsed to a single line (Markdown formatting is lost, the words are not), truncated past 4000 characters, and framed as untrusted worker-authored text; the worker still holds the full version. The happy path is unchanged — when the file really is written, the orchestrator gets the same short pointer to it as before. The previously silent no-working-directory case now logs a warning like the other two.

See [Orchestration](https://agent-deck.devopstoolkit.ai/docs/orchestration) for the troubleshooting entry, which no longer claims the summary file is always written.
